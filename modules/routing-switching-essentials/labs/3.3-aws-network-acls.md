# Lab 03 – AWS Network ACLs (NACLs)

**Objective:**  
Configure Network ACLs (NACLs) to manage subnet-level traffic control.  
You'll implement explicit allow and deny rules and compare their behavior to Security Groups.

## Step 3 – Create Custom NACLs

### a. Public NACL (for PublicSubnetA — WebServer)

1. Click **Create network ACL**.
   - **Name:** `PublicNACL`
   - **VPC:** `TrainingVPC`

2. Add **Inbound Rules** — these control traffic arriving at the public subnet from the internet:

   | Rule # | Type | Protocol | Port | Source | Allow/Deny |
   |--------|------|----------|------|--------|------------|
   | 100 | HTTP | TCP | 80 | 0.0.0.0/0 | ALLOW |
   | 110 | SSH | TCP | 22 | Your_IP/32 | ALLOW |
   | 200 | ALL | ALL | ALL | 0.0.0.0/0 | DENY |

   > Replace `Your_IP/32` with your actual public IP address (e.g. `203.0.113.5/32`). Find it at [whatismyip.com](https://whatismyip.com).

3. Add **Outbound Rules**:

   | Rule # | Type | Protocol | Port | Destination | Allow/Deny |
   |--------|------|----------|------|-------------|------------|
   | 100 | ALL | ALL | ALL | 0.0.0.0/0 | ALLOW |

   > **Why allow all outbound?** NACLs are stateless — unlike Security Groups, they do not automatically allow return traffic. Allowing all outbound ensures replies to inbound HTTP and SSH requests can leave the subnet.

4. Click **Create** then go to the **Subnet associations** tab → **Edit subnet associations** → select **PublicSubnetA** → **Save**.

---

### b. Private NACL (for PrivateSubnetB — DBServer)

1. Click **Create network ACL**.
   - **Name:** `PrivateNACL`
   - **VPC:** `TrainingVPC`

2. Add **Inbound Rules** — these control what can reach the private subnet. Only traffic originating from the public subnet (10.0.1.0/24, where WebServer lives) is permitted:

   | Rule # | Type | Protocol | Port | Source | Allow/Deny |
   |--------|------|----------|------|--------|------------|
   | 100 | MySQL | TCP | 3306 | 10.0.1.0/24 | ALLOW |
   | 110 | SSH | TCP | 22 | 10.0.1.0/24 | ALLOW |
   | 200 | ALL | ALL | ALL | 0.0.0.0/0 | DENY |

   > **Source is 10.0.1.0/24** — this is the PublicSubnet CIDR where WebServer lives. This means only traffic coming from the public subnet (i.e. from WebServer) can reach DBServer on ports 3306 and 22. All other traffic is denied by rule 200.

3. Add **Outbound Rules**:

   | Rule # | Type | Protocol | Port | Destination | Allow/Deny |
   |--------|------|----------|------|-------------|------------|
   | 100 | ALL | ALL | ALL | 0.0.0.0/0 | ALLOW |

   > **Why allow all outbound on a private subnet?** The DBServer needs to send replies back to WebServer. Because NACLs are stateless, return traffic must be explicitly allowed outbound — it is not automatic like Security Groups.

4. Click **Create** then go to **Subnet associations** → **Edit subnet associations** → select **PrivateSubnetB** → **Save**.

## Step 4 – Test Connectivity

### Test 1: SSH to WebServer from your computer
```bash
ssh -i MyAWSKey.pem ec2-user@<WebServer_Public_IP>
```
✅ Should **succeed** — PublicNACL rule 110 allows SSH from your IP.

### Test 2: Try to SSH directly to DBServer from your computer
```bash
ssh -i MyAWSKey.pem ec2-user@<DBServer_Private_IP>
```
❌ Should **fail** — PrivateNACL rule 200 denies all traffic not from 10.0.1.0/24.

### Test 3: SSH from WebServer to DBServer
Once connected to WebServer, run:
```bash
ssh ec2-user@10.0.2.10
```
✅ Should **succeed** — PrivateNACL rule 110 allows SSH from 10.0.1.0/24 (WebServer's subnet).

### Test 4: Open WebServer in browser
```
http://<WebServer_Public_IP>
```
✅ Should load — PublicNACL rule 100 allows HTTP from anywhere.

### Test 5: Modify a rule and observe the effect
1. Go to **VPC → Network ACLs → PublicNACL → Inbound rules → Edit**.
2. Change rule 100 from **ALLOW** to **DENY** for port 80.
3. Refresh your browser — the web page should now **fail to load**.
4. Revert the rule back to **ALLOW** when done.

> This demonstrates that NACLs evaluate rules in number order and stop at the first match — unlike Security Groups which evaluate all rules.

## NACLs vs Security Groups — Side by Side

| Feature | Security Group | NACL |
|---------|---------------|------|
| Level | Instance | Subnet |
| Statefulness | Stateful — return traffic automatic | Stateless — must allow return traffic explicitly |
| Rule type | Allow only | Allow and Deny |
| Rule evaluation | All rules evaluated | Rules evaluated in number order, first match wins |
| Default | Deny all inbound | Allow all inbound and outbound |
| Use together? | Yes — both apply; traffic must pass both | Yes — layered defense |

## Reflection Questions

- How are NACLs different from Security Groups?
- Why do NACLs require explicit outbound rules while Security Groups do not?
- What happens if two NACL rules conflict — for example rule 100 allows and rule 200 denies the same traffic?
- How can NACLs and Security Groups work together for defense-in-depth?
- Why is it important that the PrivateNACL uses 10.0.1.0/24 as the source rather than 0.0.0.0/0?

---

## Key Takeaways

| Concept | Description |
|---------|-------------|
| NACL | Subnet-level firewall — applies to all instances in the subnet |
| Stateless | Must explicitly allow both inbound and outbound traffic |
| Rule order | Lowest rule number evaluated first — first match wins |
| Explicit deny | Can block specific IPs or ranges — Security Groups cannot |
| Layered security | Use NACLs for subnet-wide rules, SGs for instance-specific rules |
