# Lab 03 – VPC Peering and Hybrid Connectivity

**Objective:**  
Connect two VPCs privately using **VPC Peering**, simulating a hybrid (on-premises + cloud) connection.  
You'll configure routing and verify private communication between resources in separate VPCs.

---

## Topology

```
VPC-A: TrainingVPC (10.0.0.0/16)       VPC-B: OnPremVPC (172.16.0.0/16)
┌───────────────────────┐              ┌───────────────────────┐
│ WebServer             │ ⇄ Peering ⇄  │ DBServerB             │
│ 10.0.1.x (private IP) │              │ 172.16.1.x (private)  │
└───────────────────────┘              └───────────────────────┘
```

---

## Before You Start — Confirm Existing Resources

This lab uses **TrainingVPC** and the **WebServer** instance already running from previous labs. You do not need to launch a new instance in TrainingVPC.

| Resource | Name | Expected State |
|----------|------|----------------|
| VPC | TrainingVPC | Available — 10.0.0.0/16 |
| EC2 Instance | WebServer | Running in PublicSubnetA |
| Route Table | PublicRT | Associated with PublicSubnetA |

To find WebServer's **private IP**: go to **EC2 → Instances → WebServer → Private IPv4 address**. Note this down — you will use it when testing from the peered VPC.

---

## Step 1 – Create the Second VPC (OnPremVPC)

This VPC simulates an on-premises network or a second AWS environment.

1. Go to **VPC → Your VPCs → Create VPC**.
2. Configure:
   - **Name tag:** `OnPremVPC`
   - **IPv4 CIDR block:** `172.16.0.0/16`
   - Leave all other settings as default
3. Click **Create VPC**.

### Create a subnet inside OnPremVPC
4. Go to **VPC → Subnets → Create Subnet**.
5. Configure:
   - **VPC:** `OnPremVPC`
   - **Subnet name:** `OnPremSubnetA`
   - **Availability Zone:** any
   - **IPv4 CIDR block:** `172.16.1.0/24`
6. Click **Create subnet**.

✅ You now have **TrainingVPC (10.0.0.0/16)** and **OnPremVPC (172.16.0.0/16)** — non-overlapping CIDRs, which is required for VPC Peering.

---

## Step 2 – Launch a Test Instance in OnPremVPC

You need one instance in OnPremVPC to test connectivity from the peered side.

1. Go to **EC2 → Launch Instance**.
2. Configure:
   - **Name:** `DBServerB`
   - **AMI:** Amazon Linux 2023
   - **Instance type:** t2.micro
   - **Key pair:** same key as WebServer
3. Under **Network settings → Edit**:
   - **VPC:** `OnPremVPC`
   - **Subnet:** `OnPremSubnetA`
   - **Auto-assign public IP:** Enable *(needed so you can SSH in directly for testing)*
4. Under **Firewall (Security Groups)** → Create new security group:
   - **Name:** `OnPremSG`
   - Add rules:
     | Type | Protocol | Port | Source |
     |------|----------|------|--------|
     | SSH | TCP | 22 | My IP |
     | All ICMP - IPv4 | ICMP | All | 10.0.0.0/16 |
   
   > The ICMP rule allows ping from TrainingVPC's CIDR — needed for connectivity testing.

5. Click **Launch instance**.

> **Note:** You do not need to launch a new instance in TrainingVPC. The existing **WebServer** will serve as the source for testing.

### Add ICMP rule to WebServerSG in TrainingVPC
For WebServer to receive ping replies from OnPremVPC, add an inbound rule to `WebServerSG`:

- Go to **EC2 → Security Groups → WebServerSG → Inbound rules → Edit inbound rules → Add rule**:
   | Type | Protocol | Port | Source |
   |------|----------|------|--------|
   | All ICMP - IPv4 | ICMP | All | 172.16.0.0/16 |

---

## Step 3 – Create the VPC Peering Connection

1. Go to **VPC → Peering Connections → Create Peering Connection**.
2. Configure:
   - **Name:** `Training-OnPrem-Peer`
   - **VPC ID (Requester):** `TrainingVPC (10.0.0.0/16)`
   - **VPC ID (Accepter):** `OnPremVPC (172.16.0.0/16)`
3. Click **Create Peering Connection**.
4. The status will show **Pending Acceptance**. Select the peering connection → **Actions → Accept Request → Accept**.

✅ Status should change to **Active**.

> **Why accept manually?** In a real cross-account peering, the accepting account must explicitly approve the request. Even in the same account, AWS requires this confirmation step.

---

## Step 4 – Update Route Tables in Both VPCs

Peering alone does not route traffic — you must add routes in both VPCs pointing to the peering connection.

### In TrainingVPC — update PublicRT
1. Go to **VPC → Route Tables**.
2. Select **PublicRT** (associated with PublicSubnetA where WebServer lives).
3. Click **Routes → Edit routes → Add route**:
   - **Destination:** `172.16.0.0/16`
   - **Target:** select **Peering Connection** → choose `Training-OnPrem-Peer`
4. Click **Save changes**.

### In OnPremVPC — update its route table
1. Find the route table associated with `OnPremSubnetA`.
2. Click **Routes → Edit routes → Add route**:
   - **Destination:** `10.0.0.0/16`
   - **Target:** select **Peering Connection** → choose `Training-OnPrem-Peer`
3. Click **Save changes**.

> **Why update both?** VPC Peering is not automatic — each VPC needs an explicit route telling it where to send traffic destined for the other VPC's CIDR.

## Step 5 – Test Private Connectivity

### Test 1: From WebServer, ping DBServerB
SSH into WebServer:
```bash
ssh -i MyAWSKey.pem ec2-user@<WebServer_Public_IP>
```

Then ping DBServerB using its **private IP** (check EC2 console for the actual IP):
```bash
ping <DBServerB_Private_IP>
```
✅ Expected: successful ping replies — traffic is routing across the peering connection.

### Test 2: From DBServerB, ping WebServer
SSH into DBServerB:
```bash
ssh -i MyAWSKey.pem ec2-user@<DBServerB_Public_IP>
```

Then ping WebServer using its **private IP**:
```bash
ping <WebServer_Private_IP>
```
✅ Expected: successful ping replies in both directions.

### Test 3: Confirm internet isolation from private side
From DBServerB, try reaching the internet:
```bash
curl http://google.com
```
❌ Expected: this will fail if no IGW or NAT is attached to OnPremVPC — confirming private-only connectivity through peering.

## Step 6 – Optional: Use VPC Reachability Analyzer

Reachability Analyzer traces the network path between two resources without sending real traffic.

1. Go to **VPC → Reachability Analyzer → Create and analyze path**.
2. Configure:
   - **Source type:** Instance → select `WebServer`
   - **Destination type:** Instance → select `DBServerB`
   - **Protocol:** ICMP
3. Click **Create and analyze path**.

✅ Expected: path shows **Reachable** via the peering connection, confirming routing is correct end to end.

## Reflection

- Why is VPC Peering **non-transitive**? If VPC-A peers with VPC-B and VPC-B peers with VPC-C, can VPC-A reach VPC-C?
- How does VPC Peering differ from a **VPN connection**?
- What would you need to add to give DBServerB internet access without making it publicly accessible?
- What are use cases for **AWS PrivateLink** compared to VPC Peering?

---

## Key Takeaways

| Concept | Description |
|---------|-------------|
| VPC Peering | Private connection between two VPCs — traffic stays on AWS backbone |
| Non-transitive | Peering is point-to-point — A↔B and B↔C does not mean A↔C |
| Route tables | Both sides must have explicit routes pointing to the peering connection |
| Security Groups | Must allow traffic from the peered VPC's CIDR — peering alone is not enough |
| Non-overlapping CIDRs | Both VPCs must have different CIDR blocks — peering fails if they overlap |
