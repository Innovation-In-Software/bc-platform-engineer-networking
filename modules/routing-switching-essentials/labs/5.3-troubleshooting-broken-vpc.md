# Lab 03 – Troubleshooting Common VPC Issues

**Objective:**  
Learn to identify and fix three common networking problems in AWS environments:  
1. **Private instances can't reach the Internet** (NAT Gateway missing)  
2. **ALB shows unhealthy targets** (Security Group and health check misconfiguration)  
3. **VPC peering traffic fails** (Route Table misconfigured)

---

Internet

   IGW

│              MainVPC (10.0.0.0/16)           │

## Step 1 – Build the Working Environment

Complete all sub-steps in order. Verify each step works before moving to Step 2.

### 1a. Create MainVPC

1. Go to **VPC → Your VPCs → Create VPC**.
2. Configure:
   - **Name:** `MainVPC`
   - **IPv4 CIDR:** `10.0.0.0/16`
3. Click **Create VPC**.

### 1b. Create Subnets

1. Go to **VPC → Subnets → Create Subnet**.
2. Select **MainVPC** and add two subnets:

   | Name | AZ | CIDR |
   |------|----|------|
   | PublicSubnet | us-east-1a | 10.0.1.0/24 |
   | PrivateSubnet | us-east-1b | 10.0.2.0/24 |

3. After creation, select **PublicSubnet** → **Actions → Edit subnet settings** → enable **Auto-assign public IPv4** → Save.
4. Leave **PrivateSubnet** with auto-assign disabled — private instances should have no public IP.

### 1c. Create Internet Gateway

1. Go to **VPC → Internet Gateways → Create internet gateway**.
   - **Name:** `MainIGW`
2. Select it → **Actions → Attach to VPC → MainVPC**.

### 1d. Create NAT Gateway

The NAT Gateway allows private instances to initiate outbound internet connections without being publicly accessible.

1. Go to **VPC → NAT Gateways → Create NAT Gateway**.
2. Configure:
   - **Name:** `MainNAT`
   - **Subnet:** `PublicSubnet` — NAT Gateway must be in a public subnet
   - **Connectivity type:** Public
   - **Elastic IP:** click **Allocate Elastic IP**
3. Click **Create NAT Gateway** — wait until status shows **Available** (2–3 minutes).

### 1e. Configure Route Tables

1. Go to **VPC → Route Tables**.
2. Find the route table associated with **PublicSubnet** — rename it `PublicRT`.
3. Add route: **Routes → Edit routes → Add route**:
   - Destination: `0.0.0.0/0` → Target: `MainIGW`
4. Find the route table associated with **PrivateSubnet** (or create a new one named `PrivateRT` and associate it).
5. Add route: **Routes → Edit routes → Add route**:
   - Destination: `0.0.0.0/0` → Target: `MainNAT`

### 1f. Create PartnerVPC

1. Go to **VPC → Create VPC**.
2. Configure:
   - **Name:** `PartnerVPC`
   - **IPv4 CIDR:** `172.16.0.0/16`
3. Click **Create VPC**.
4. Create a subnet inside PartnerVPC:
   - **Name:** `PartnerSubnet`
   - **AZ:** us-east-1a
   - **CIDR:** `172.16.1.0/24`
   - Enable auto-assign public IPv4

### 1g. Create and Accept VPC Peering Connection

1. Go to **VPC → Peering Connections → Create Peering Connection**.
2. Configure:
   - **Name:** `Main-Partner-Peer`
   - **Requester VPC:** `MainVPC`
   - **Accepter VPC:** `PartnerVPC`
3. Click **Create Peering Connection**.
4. Select the pending connection → **Actions → Accept Request → Accept**.

✅ Status should change to **Active**.

5. Add peering routes:
   - **PublicRT** (MainVPC): add `172.16.0.0/16` → `Main-Partner-Peer`
   - **PrivateRT** (MainVPC): add `172.16.0.0/16` → `Main-Partner-Peer`
   - **PartnerVPC route table**: add `10.0.0.0/16` → `Main-Partner-Peer`

### 1h. Create Security Groups

1. Create **WebSG** in `MainVPC`:

   | Type | Protocol | Port | Source |
   |------|----------|------|--------|
   | SSH | TCP | 22 | My IP |
   | HTTP | TCP | 80 | 0.0.0.0/0 |
   | All ICMP - IPv4 | ICMP | All | 172.16.0.0/16 |

2. Create **TestSG** in `PartnerVPC`:

   | Type | Protocol | Port | Source |
   |------|----------|------|--------|
   | SSH | TCP | 22 | My IP |
   | All ICMP - IPv4 | ICMP | All | 10.0.0.0/16 |

### 1i. Launch EC2 Instances

| Instance | VPC | Subnet | Security Group | Public IP |
|----------|-----|--------|---------------|-----------|
| WebServer1 | MainVPC | PublicSubnet | WebSG | Yes |
| WebServer2 | MainVPC | PrivateSubnet | WebSG | No |
| TestServer | PartnerVPC | PartnerSubnet | TestSG | Yes |

For each instance: **EC2 → Launch Instance → Amazon Linux 2023, t2.micro**, select the correct VPC, subnet, and SG.

### 1j. Install Apache on WebServer1 and WebServer2

SSH into **WebServer1** (via public IP), then run:
```bash
sudo yum install -y httpd
echo "<h1>Server $(hostname)</h1>" | sudo tee /var/www/html/index.html
sudo systemctl start httpd
sudo systemctl enable httpd
```

For **WebServer2**, SSH via WebServer1 (it has no public IP):
```bash
# From WebServer1
ssh ec2-user@<WebServer2_Private_IP>
# Then run the same commands above
```

### 1k. Create the Application Load Balancer

> **Important:** An internet-facing ALB must be placed in **public subnets only**. Do not add the private subnet to the ALB.

1. Go to **EC2 → Load Balancers → Create Load Balancer → Application Load Balancer**.
2. Configure:
   - **Name:** `MainALB`
   - **Scheme:** Internet-facing
3. Under **Network mapping**:
   - **VPC:** `MainVPC`
   - **Subnets:** select **PublicSubnet only** (us-east-1a)

   > Since MainVPC only has one public subnet, the ALB will be in a single AZ. This is acceptable for this lab — in production you would have public subnets in multiple AZs.

4. **Security Group:** select `WebSG`.
5. Create a **Target Group**:
   - **Name:** `MainTG`
   - **Protocol:** HTTP, **Port:** 80
   - **Health check path:** `/`
   - Add **both WebServer1 and WebServer2** as targets
6. Under **Listeners:** HTTP:80 → forward to `MainTG`.
7. Click **Create load balancer**.

### 1l. Verify Everything Works

Run all these checks before proceeding to Step 2:

```bash
# From your local machine — SSH to WebServer1
ssh -i MyAWSKey.pem ec2-user@<WebServer1_Public_IP>

# From WebServer1 — SSH to WebServer2
ssh ec2-user@<WebServer2_Private_IP>

# From WebServer2 — confirm internet access via NAT
curl -I http://google.com

# From WebServer1 — confirm VPC peering
ping <TestServer_Private_IP>
```

Also open the ALB DNS name in your browser — both WebServer1 and WebServer2 should respond.

✅ All tests pass — your environment is working correctly. Take note of TestServer's **private IP** from EC2 console — you'll need it in Scenario 3.

## Step 2 – Break the Environment

> **Read this entire step before executing anything.** You are about to deliberately break three things. Each break corresponds to one problem scenario in Step 3. Do all three breaks before attempting any fixes.

### Break 1: Remove NAT Gateway internet access for private instances
1. Go to **VPC → NAT Gateways → MainNAT → Actions → Delete NAT Gateway → Confirm**.
2. Go to **VPC → Route Tables → PrivateRT → Routes → Edit routes**.
3. Delete the `0.0.0.0/0` route.

### Break 2: Break ALB health checks
4. Go to **EC2 → Target Groups → MainTG → Health checks → Edit**.
5. Change **Health check path** from `/` to `/health` → Save.
6. Go to **EC2 → Security Groups → WebSG → Inbound rules → Edit inbound rules**.
7. Delete the **HTTP port 80** rule → Save.

### Break 3: Remove VPC peering routes
8. Go to **VPC → Route Tables → PublicRT → Routes → Edit routes**.
9. Delete the `172.16.0.0/16` route.
10. Go to **VPC → Route Tables → PrivateRT → Routes → Edit routes**.
11. Delete the `172.16.0.0/16` route.
12. Go to **PartnerVPC route table → Routes → Edit routes**.
13. Delete the `10.0.0.0/16` route.

✅ Your environment is now broken in three distinct ways. Proceed to Step 3 to diagnose and fix each one.

## Problem Scenario 1 – Private Instance Can't Reach Internet

### Symptom
WebServer2 (in PrivateSubnet) cannot reach external services or download updates.

### Diagnose
SSH to WebServer1, then hop to WebServer2:
```bash
ssh -i MyAWSKey.pem ec2-user@<WebServer1_Public_IP>
ssh ec2-user@<WebServer2_Private_IP>
```

From WebServer2, test internet:
```bash
curl -I http://google.com
ping 8.8.8.8
```
❌ Both time out.

Check the private route table:
```
VPC → Route Tables → PrivateRT → Routes
```
**Finding:** No `0.0.0.0/0` route exists — private instances have no path to the internet.

Also check NAT Gateways:
```
VPC → NAT Gateways
```
**Finding:** `MainNAT` is deleted.

### Fix
1. Go to **VPC → NAT Gateways → Create NAT Gateway**.
2. Configure:
   - **Name:** `MainNAT-Fixed`
   - **Subnet:** `PublicSubnet`
   - **Connectivity type:** Public
   - **Elastic IP:** Allocate new
3. Wait until status is **Available**.
4. Go to **VPC → Route Tables → PrivateRT → Routes → Edit routes → Add route**:
   - Destination: `0.0.0.0/0` → Target: `MainNAT-Fixed`

### Verify
From WebServer2:
```bash
curl -I http://google.com
```
✅ HTTP response received.

**Lesson:** NAT Gateway must exist in a public subnet and the private route table must point `0.0.0.0/0` at it. Without both, private instances are fully internet-isolated.

## Problem Scenario 2 – ALB Shows Unhealthy Targets

### Symptom
Browsing to the ALB DNS name returns a 503 error. The target group shows both instances as Unhealthy.

### Diagnose

Check target health:
```
EC2 → Target Groups → MainTG → Targets tab
```
**Finding:** Both targets show `Health status: Unhealthy`.

Check health check configuration:
```
EC2 → Target Groups → MainTG → Health checks tab
```
**Finding:** Health check path is `/health` — but the web servers only serve content on `/`.

Check the security group:
```
EC2 → Security Groups → WebSG → Inbound rules
```
**Finding:** HTTP port 80 inbound rule is missing — the ALB cannot reach the instances.

### Fix

1. Fix the health check path:
   - **EC2 → Target Groups → MainTG → Health checks → Edit**
   - Change path from `/health` to `/`
   - Click **Save changes**

2. Restore the HTTP rule:
   - **EC2 → Security Groups → WebSG → Inbound rules → Edit inbound rules → Add rule**:

   | Type | Protocol | Port | Source |
   |------|----------|------|--------|
   | HTTP | TCP | 80 | 0.0.0.0/0 |

   - Click **Save rules**

### Verify
Wait 2–3 minutes for health checks to run, then:
```
EC2 → Target Groups → MainTG → Targets tab
```
✅ Both targets show `Health status: Healthy`.

Browse to the ALB DNS name — page loads successfully.

**Lesson:** Two separate issues caused unhealthy targets — the wrong health check path AND a missing security group rule. Both must be fixed. Always check both the health check config and the security group when targets are unhealthy.

## Problem Scenario 3 – VPC Peering Traffic Fails

### Symptom
Cannot ping or SSH from WebServer1 in MainVPC to TestServer in PartnerVPC, even though the peering connection shows Active.

### Diagnose

Verify the peering connection:
```
VPC → Peering Connections → Main-Partner-Peer
```
**Finding:** Status is **Active** — the connection itself is fine.

Test connectivity from WebServer1:
```bash
ping <TestServer_Private_IP>
```
❌ No response.

Check MainVPC route tables:
```
VPC → Route Tables → PublicRT → Routes
VPC → Route Tables → PrivateRT → Routes
```
**Finding:** No route for `172.16.0.0/16` in either route table.

Check PartnerVPC route table:
```
VPC → Route Tables → (PartnerVPC route table) → Routes
```
**Finding:** No route for `10.0.0.0/16`.

### Fix

1. Go to **VPC → Route Tables → PublicRT → Routes → Edit routes → Add route**:
   - Destination: `172.16.0.0/16` → Target: Peering Connection → `Main-Partner-Peer`

2. Go to **VPC → Route Tables → PrivateRT → Routes → Edit routes → Add route**:
   - Destination: `172.16.0.0/16` → Target: Peering Connection → `Main-Partner-Peer`

3. Go to **PartnerVPC route table → Routes → Edit routes → Add route**:
   - Destination: `10.0.0.0/16` → Target: Peering Connection → `Main-Partner-Peer`

### Verify
From WebServer1:
```bash
ping <TestServer_Private_IP>
```
✅ Ping succeeds.

```bash
ssh ec2-user@<TestServer_Private_IP>
```
✅ SSH succeeds.

**Lesson:** An Active peering connection does not route traffic automatically. Both VPCs need explicit route table entries pointing at the peering connection — without both sides, traffic has no path.

## Troubleshooting Best Practices

### Systematic Approach
1. **Layer by layer:** confirm physical link → routing → security groups → application
2. **Inside-out:** start at the source instance, trace the path hop by hop to the destination
3. **One change at a time:** fix one thing, test, then move to the next

### Useful AWS Tools
- **VPC Reachability Analyzer** — traces the path between two resources without sending real traffic
- **VPC Flow Logs** — captures accept/reject decisions for every packet at the subnet or ENI level
- **CloudWatch** — metrics and alarms for ALB target health, NAT Gateway traffic, VPN tunnel state

### Common Debugging Commands
```bash
# Test reachability
ping <destination>
curl -I http://<url>

# Check routing
ip route show

# Check DNS
nslookup <hostname>

# AWS CLI
aws ec2 describe-route-tables --filters Name=vpc-id,Values=<vpc-id>
aws ec2 describe-security-groups --group-ids <sg-id>
aws elbv2 describe-target-health --target-group-arn <arn>
```
