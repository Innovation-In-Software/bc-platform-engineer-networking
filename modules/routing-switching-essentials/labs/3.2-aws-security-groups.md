# Lab 02 – Understanding and Configuring AWS Security Groups

**Objective:**  
Learn how to configure and test Security Groups (SGs) in AWS to control inbound and outbound traffic at the **instance level**.  
You'll secure a web server and a database server within a VPC and observe how SGs enforce Layer 4 rules.

## Step 2 – Verify Existing Security Groups

During Lab 01, you created `WebServerSG` and `DBServerSG` as part of the EC2 launch wizard. Before adding or changing rules, verify what is already configured.

### a. Verify WebServerSG
1. Go to **EC2 → Security Groups**.
2. Select **WebServerSG**.
3. Click the **Inbound rules** tab and confirm the following rules exist:

   | Type | Protocol | Port | Source |
   |------|-----------|-------|--------|
   | SSH | TCP | 22 | Your public IP |
   | HTTP | TCP | 80 | 0.0.0.0/0 |

4. If either rule is missing, click **Edit inbound rules → Add rule** and add it.

### b. Verify DBServerSG
1. Select **DBServerSG** from the Security Groups list.
2. Click the **Inbound rules** tab and confirm:

   | Type | Protocol | Port | Source |
   |------|-----------|-------|--------|
   | SSH | TCP | 22 | WebServerSG |
   | MySQL/Aurora | TCP | 3306 | WebServerSG |

3. If either rule is missing, click **Edit inbound rules → Add rule**.  
   For the **Source** field, select **Custom** and search for `WebServerSG` by name — this references the security group directly rather than a static IP.

> **Why reference a SG as source instead of an IP?**  
> Using `WebServerSG` as the source means any instance assigned that SG can connect — even if the instance is replaced and gets a new IP. This is more resilient than a hard-coded IP range.

## Step 4 – Test Security Group Rules

### Test 1: SSH into WebServer from your local machine
```bash
chmod 400 MyAWSKey.pem
ssh -i MyAWSKey.pem ec2-user@<WebServer_Public_IP>
```
✅ Should **succeed** — WebServerSG allows SSH from your IP.

### Test 2: From WebServer, SSH into DBServer
Once connected to WebServer, run:
```bash
ssh ec2-user@10.0.2.10
```
✅ Should **succeed** — DBServerSG allows SSH from WebServerSG.

> **Note:** For this to work you need your key available on WebServer. Either use SSH agent forwarding (`ssh -A`) or copy the key to WebServer first.

### Test 3: From your local machine, try SSHing directly to DBServer
```bash
ssh -i MyAWSKey.pem ec2-user@<DBServer_Private_IP>
```
❌ Should **fail** — DBServer has no public IP and DBServerSG does not allow connections from outside the VPC.

### Test 4: Open WebServer in a browser
```
http://<WebServer_Public_IP>
```
✅ Should load — WebServerSG allows HTTP (port 80) from anywhere.

> **Note:** If the page doesn't load, a web server application (e.g. Apache) may not be running on the instance. The SG rule is correct but there is nothing listening on port 80 yet. This is expected at this stage.

## Reflection Questions

- What is the difference between a Security Group and a traditional firewall rule?
- Why is it better to reference a Security Group as a source rather than a CIDR block?
- Security Groups are stateful — what does that mean for return traffic?
- What would happen if you removed the outbound allow-all rule from DBServerSG?

---

## Key Takeaways

| Concept | Description |
|---------|-------------|
| Security Group | Virtual firewall at the instance level |
| Stateful | Return traffic is automatically allowed — no explicit outbound rule needed |
| Default Behavior | Deny all inbound, allow all outbound |
| SG as Source | Reference another SG instead of an IP for resilient rules |
| Best Practice | One SG per function (web, db, bastion, etc.) |
