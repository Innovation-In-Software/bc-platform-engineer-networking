# Lab 09 – SNMP, Syslog & NTP Configuration

**Objective:**  
Configure three core network management protocols on a Cisco router and verify each one using IOS show commands. You will set up NTP so the router synchronises its clock, Syslog so log messages are sent to a central server, and SNMP so a management tool can query the router for performance data and receive alerts.

> **Packet Tracer note:** NTP works fully in this lab. Syslog and SNMP configuration on the router works fully and is verifiable with show commands — however Packet Tracer's server does not reliably display received syslog messages or SNMP traps the way a real tool like PRTG or SolarWinds would. The router-side configuration is the exam-relevant skill and is what you will verify here.

## Part 1 — NTP (Network Time Protocol)

> **Packet Tracer support: Full.** NTP works completely — synchronisation state, show commands, and clock updates all behave as on real hardware.

### Why NTP matters
Without synchronised clocks, log timestamps on different devices can differ by minutes or hours. When investigating an incident across multiple devices you need to know the exact order events occurred. NTP ensures every device agrees on the time.

### Step 2. Check the router clock before NTP

```
Router0# show clock
```

**Expected output (unsynchronised):**
```
*00:04:23.456 UTC Mon Mar 1 1993
```

The `*` before the time means the clock is **not synchronised** — running from the device's internal clock which has drifted since manufacture.

Record the time shown: _______________

### Step 3. Enable NTP on Server0

Click **Server0 → Services → NTP**:
1. Toggle NTP service to **On**

### Step 4. Configure Router0 to use Server0 as NTP server

```
Router0# configure terminal
Router0(config)# ntp server 192.168.2.10
Router0(config)# exit
```

### Step 5. Verify NTP synchronisation

Wait 30–60 seconds then check:

```
Router0# show ntp status
```

**Expected output:**
```
Clock is synchronized, stratum 2, reference is 192.168.2.10
```

- `Clock is synchronized` — locked to the NTP server
- `stratum 2` — two hops from a stratum 1 source
- `reference is 192.168.2.10` — the NTP source IP

```
Router0# show ntp associations
```

**Expected output:**
```
address         ref clock       st   when   poll reach  delay  offset  disp
*~192.168.2.10  127.127.1.1     1    12     64   377    1.0    0.5     0.5
```

The `*` means this is the selected NTP source.

```
Router0# show clock
```

The `*` before the time should now be gone — the clock is synchronised.

## Part 2 — Syslog

> **Packet Tracer support: Router side fully works.** The `logging host`, `logging trap`, and `service timestamps` commands configure correctly and are verifiable with `show logging`. The server's syslog display tab may not show received messages reliably depending on your Packet Tracer version — this is a known simulator limitation. Focus your verification on the router side.

### Why Syslog matters
By default IOS stores log messages in a local buffer that is lost on reload. Syslog sends those messages to a central server for permanent storage, searchable across all devices in one place.

### Step 6. Check existing logs

```
Router0# show logging
```

Note the current buffer contents. You will compare this after configuration.

### Step 7. Enable Syslog service on Server0

Click **Server0 → Services → Syslog** and toggle the service to **On**.

### Step 8. Configure Syslog on Router0

```
Router0# configure terminal

Router0(config)# logging host 192.168.2.10
Router0(config)# logging trap warnings
Router0(config)# service timestamps log datetime msec

Router0(config)# exit
```

> **Severity levels:**
> 0=Emergency | 1=Alert | 2=Critical | 3=Error | 4=Warning | 5=Notice | 6=Informational | 7=Debug
>
> `logging trap warnings` sends levels 0–4. Never send level 7 (Debug) to a production syslog server — it generates enormous volume.

### Step 9. Generate log events

Shut and re-enable an interface to create a log message:

```
Router0# configure terminal
Router0(config)# interface GigabitEthernet0/0/0
Router0(config-if)# shutdown
Router0(config-if)# no shutdown
Router0(config-if)# exit
```

You should see console messages like:
```
%LINEPROTO-5-UPDOWN: Line protocol on Interface GigabitEthernet0/0/0, changed state to down
%LINEPROTO-5-UPDOWN: Line protocol on Interface GigabitEthernet0/0/0, changed state to up
```

### Step 10. Verify Syslog on Router0

```
Router0# show logging
```

**Look for these lines confirming correct configuration:**
```
Logging to 192.168.2.10 (udp port 514, audit disabled, link up)
    2 message lines logged
```

Also confirm timestamps are enabled:
```
Router0# show running-config | include timestamps
```
Should show: `service timestamps log datetime msec`

> **Server display:** Check **Server0 → Services → Syslog** to see if messages appear. If the tab is empty this is a Packet Tracer limitation — your router configuration is still correct and verified by `show logging`.

### Syslog Verification Table — fill this in
| Check | Command | Result |
|-------|---------|--------|
| Logging destination configured | `show logging` | Shows 192.168.2.10? |
| Severity level set | `show logging` | Trap level = warnings? |
| Timestamps enabled | `show run \| include timestamps` | Present? |
| Log events generated | Console output | Up/down messages seen? |

## Part 3 — SNMP

> **Packet Tracer support: Router configuration fully works.** All snmp-server commands configure correctly and are verifiable with show commands. The Packet Tracer server does not function as a real SNMP manager — it will not respond to GET requests or display received TRAPs the way tools like PRTG, SolarWinds, or Zabbix do. In a production environment or the Network Automation Tools course you will work with real SNMP managers. Here the focus is on correct router configuration.

### Why SNMP matters
Syslog tells you what happened after the fact. SNMP lets a management tool actively poll devices for real-time data — CPU, interface counters, memory — and receive instant TRAPs when something changes without waiting to be asked.

### Step 11. Enable SNMP service on Server0

Click **Server0 → Services → SNMP** and toggle the service to **On**.

### Step 12. Configure SNMP on Router0

```
Router0# configure terminal

Router0(config)# snmp-server community PUBLIC ro
Router0(config)# snmp-server contact admin@lab.local
Router0(config)# snmp-server location Lab-Room-1
Router0(config)# snmp-server host 192.168.2.10 traps version 2c PUBLIC
Router0(config)# snmp-server enable traps snmp linkdown linkup

Router0(config)# exit
```

> **Community string note:** `PUBLIC` is the standard lab community string. In production always use a long random string — the community string is the SNMP password and is sent in plain text in SNMPv2c. SNMPv3 adds encryption and is required in secure environments.

### Step 13. Verify SNMP configuration

```
Router0# show snmp
```

**Look for:**
- Contact and location fields populated
- SNMP packets input/output counters
- Trap destination listed

```
Router0# show snmp community
```

Should show `PUBLIC` with `RO` (read-only) access.

```
Router0# show running-config | section snmp
```

Should show all five snmp-server lines you configured.

### Generate a TRAP event

Shut and re-enable an interface — this triggers a linkdown/linkup TRAP to Server0:

```
Router0# configure terminal
Router0(config)# interface GigabitEthernet0/0/0
Router0(config-if)# shutdown
Router0(config-if)# no shutdown
Router0(config-if)# exit
```

## Reflection Questions

1. Why should NTP be configured before Syslog? What problem does it solve for log analysis?
2. You configure `logging trap informational` instead of `logging trap warnings`. What changes and why might this cause problems on a busy router?
3. The SNMP community string `PUBLIC` is read-only. What could an attacker do if they discovered it on a production device — and what would they need to do real damage?
4. What is the difference between SNMP polling and SNMP TRAPs, and why do monitoring systems use both?
5. A network engineer checks the syslog server and sees an interface went down at 03:14 on Router0 but at 03:22 on Router1 for the same physical event. What caused this and how does NTP fix it?

## Summary

| Protocol | Port | Purpose | Key Command |
|----------|------|---------|-------------|
| NTP | UDP 123 | Synchronise device clocks | `ntp server <ip>` |
| Syslog | UDP 514 | Send log messages to central server | `logging host <ip>` |
| SNMP | UDP 161/162 | Poll devices and receive alerts | `snmp-server community` |

| Verification Command | What It Shows |
|---------------------|---------------|
| `show clock` | Current time and synchronisation status |
| `show ntp status` | Whether clock is synchronised and stratum |
| `show ntp associations` | NTP server and poll statistics |
| `show logging` | Log buffer and remote destinations |
| `show snmp` | Statistics, contact, location |
| `show snmp community` | Community strings and access level |
