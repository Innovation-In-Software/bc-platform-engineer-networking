## Step 4. Fault 1 — Wrong Subnet Mask on PC1

### Symptoms
PC0 can ping the gateway (192.168.10.1) but pings to PC1 (192.168.10.11) behave unexpectedly — PC1 may not respond correctly to hosts outside its perceived local subnet.

### How to find it

On PC1 → **Desktop** → **Command Prompt:**
```
C:\> ipconfig
```
- **Look for:** The subnet mask next to the IP address

On PC0, run:
```
C:\> ping 192.168.10.11
C:\> tracert 192.168.10.11
```
- If tracert shows the traffic going to the gateway instead of directly to PC1, the mask is wrong

### Root cause
PC1 is configured with `255.255.0.0` (/16) instead of `255.255.255.0` (/24). PC1 thinks hosts on 192.168.20.x are on the same local network and tries to ARP for them directly instead of using the gateway.

### Fix
Click **PC1** → **Desktop** → **IP Configuration** → change Subnet Mask to:

| Field | Incorrect Value | Correct Value |
|-------|----------------|---------------|
| Subnet Mask | 255.255.0.0 | 255.255.255.0 |

### Verify
```
C:\> ping 192.168.10.10
C:\> ping 192.168.10.1
```
Both should succeed with 0% loss.

## Step 5. Fault 2 — ACL Blocking ICMP

### Symptoms
PC0 can ping its own gateway (192.168.10.1). PC2 can ping Router1 (192.168.20.1). But pings from PC2 → PC0 time out, even though the routing table is correct.

### How to find it

On Router0 → **CLI:**
```
Router0# show ip access-lists
Router0# show ip interface g0/0/0
```
- `show ip access-lists` will show the ACL entries and hit counters
- `show ip interface` will show which ACL is applied and in which direction

**Expected output showing the fault:**
```
Extended IP access list BLOCK_REMOTE
    10 deny icmp 192.168.20.0 0.0.0.255 any (X matches)
    20 permit ip any any
```

Also run traceroute from PC2:
```
C:\> tracert 192.168.10.10
```
- Traffic reaches Router0 but gets no reply — consistent with an inbound ACL on G0/0/0 dropping ICMP from 192.168.20.0/24

### Root cause
An extended ACL named `BLOCK_REMOTE` has a `deny icmp` entry that drops all ICMP (ping) packets originating from 192.168.20.0/24. It is applied inbound on Router0's G0/0/0, meaning it also filters traffic arriving from the WAN side.

### Fix
Remove the deny ICMP entry from the ACL on Router0:

```
Router0# configure terminal
Router0(config)# ip access-list extended BLOCK_REMOTE
Router0(config-ext-nacl)# no deny icmp 192.168.20.0 0.0.0.255 any
Router0(config-ext-nacl)# exit
```

### Verify
```
Router0# show ip access-lists BLOCK_REMOTE
```
- **Expected:** Only the `permit ip any any` entry remains, with no deny icmp line

From PC2:
```
C:\> ping 192.168.10.10
```
- **Expected:** 4 replies

## Step 6. Fault 3 — Wrong Default Gateway on SW0

### Symptoms
You cannot ping SW0's management IP (192.168.10.50) from Router0 or any remote host, even though SW0 itself can ping locally. Remote pings to SW0 time out.

### How to find it

On SW0 → **CLI:**
```
SW0# show running-config | include default-gateway
SW0# show ip default-gateway
```
- **Expected output showing the fault:**
```
ip default-gateway 192.168.10.99
```
- 192.168.10.99 does not exist — SW0 has no valid path off its local subnet

Also try from Router0:
```
Router0# ping 192.168.10.50
```
- Times out — SW0 receives the ping but cannot route the reply back because the gateway is wrong

### Root cause
SW0's management VLAN default gateway is set to `192.168.10.99` instead of `192.168.10.1` (Router0's LAN interface). SW0 can receive traffic but cannot send replies off-subnet.

### Fix
```
SW0# configure terminal
SW0(config)# no ip default-gateway 192.168.10.99
SW0(config)# ip default-gateway 192.168.10.1
SW0(config)# exit
```

### Verify
```
SW0# show ip default-gateway
```
- **Expected:** `192.168.10.1`

From Router0:
```
Router0# ping 192.168.10.50
```
- **Expected:** 4 replies from SW0's management IP

## Step 7. Fault 4 — Wrong DNS Server in DHCP Scope

### Symptoms
PCs on LAN1 (192.168.10.x) receive an IP address via DHCP but cannot resolve domain names. `ping google.com` fails with "Unknown host" while `ping 8.8.8.8` succeeds.

### How to find it

On PC0, release and renew DHCP then check the assigned DNS server:
```
C:\> ipconfig /release
C:\> ipconfig /renew
C:\> ipconfig /all
```
- **Look for:** The DNS Server line — it should show `8.8.8.8` but will show `8.8.4.99`

On Router0 → **CLI:**
```
Router0# show running-config | section dhcp
```
- **Expected output showing the fault:**
```
ip dhcp pool LAN1
   network 192.168.10.0 255.255.255.0
   default-router 192.168.10.1
   dns-server 8.8.4.99
```

### Root cause
The DHCP pool on Router0 is distributing `8.8.4.99` as the DNS server address. The correct Google DNS address is `8.8.4.4` (or `8.8.8.8`). Clients receive a valid IP but DNS queries go to a non-existent server.

### Fix
```
Router0# configure terminal
Router0(config)# ip dhcp pool LAN1
Router0(dhcp-config)# dns-server 8.8.8.8
Router0(dhcp-config)# exit
```

On PC0, renew the DHCP lease to pick up the new DNS server:
```
C:\> ipconfig /release
C:\> ipconfig /renew
C:\> ipconfig /all
```

### Verify
```
C:\> ping cisco.com
```
- **Expected:** DNS resolves and pings succeed (or replies from Cisco's servers)

## Troubleshooting Reference

Use this as a quick guide when stuck:

| Symptom | Where to Look | Command |
|---------|--------------|---------|
| No link light | Layer 1 — cable or port | Check physical connections |
| Ping same subnet fails | Layer 2 — ARP, VLAN | `show arp`, `show mac address-table` |
| Ping gateway fails | Layer 3 — IP config | `ipconfig`, `show ip int brief` |
| Gateway ok, remote fails | Layer 3 — routing or ACL | `show ip route`, `show ip access-lists` |
| Routing correct, still fails | ACL filtering | `show ip access-lists`, check hit counters |
| Pings work, names don't | Layer 7 — DNS | `ipconfig /all`, check dns-server in DHCP |
| SW management unreachable | Switch gateway | `show ip default-gateway` |

### Key Cisco IOS Commands Used in This Lab
```
show ip interface brief          ! all interfaces, IPs, and status
show ip route                    ! routing table (C=connected, S=static)
show ip access-lists             ! ACL entries and hit counters
show running-config | section    ! filter config by keyword
show ip default-gateway          ! management gateway on switches
show arp                         ! IP-to-MAC mappings
ping <ip>                        ! test Layer 3 reachability
traceroute <ip>                  ! identify where packets are dropped
```

## Summary

| Concept | Description |
|---------|-------------|
| Structured troubleshooting | Define → gather → analyze → test ONE change → document |
| OSI-based approach | No link = L1; wrong VLAN = L2; bad IP/route = L3; ACL = L3/L4; DNS = L7 |
| Subnet mask impact | Wrong mask changes what a host considers "local" vs "remote" traffic |
| ACL hit counters | `show ip access-lists` reveals which ACE is matching traffic |
| DHCP DNS field | Clients use whatever DNS IP the DHCP server hands them |
| Switch management gateway | Required for the switch to send replies off its local subnet |
